Three secret stores, one job each: the **ssh-agent** holds decrypted SSH keys
for the session, **gpg-agent** caches the key that unlocks `pass`, and
**gnome-keyring** serves desktop apps that use the Secret Service API. The
symptom table for all three is in [troubleshooting](./troubleshooting.html);
this guide is the how-to.

## SSH: the personal key and the session agent

`~/.ssh/id_ed25519` is the everyday key (GitHub and everything else). A plain
OpenSSH `ssh-agent` runs as a systemd user unit on `$XDG_RUNTIME_DIR/ssh-agent`
and `SSH_AUTH_SOCK` points there in every session. With the system-wide
`AddKeysToAgent yes`, the first `ssh` or `git push` of the session shows the
passphrase dialog, the decrypted key lands in the agent, and every later
connection is silent until logout.

```bash
ssh-add -l                                  # what the agent holds (comment + type)
systemctl --user status ssh-agent.service
```

This agent is the only one allowed to export `SSH_AUTH_SOCK`: `gcr-ssh-agent`
(gnome-keyring's) is deliberately off because its prompter cannot be styled.
Do not re-enable it, `programs.ssh.startAgent`, or gpg's SSH support. Nothing
listens for incoming SSH either; `services.openssh` is off on purpose.

## The passphrase dialog

Prompts are a Nord fuzzel password dialog (`ssh-askpass-fuzzel`, set as
`SSH_ASKPASS`). `SSH_ASKPASS_REQUIRE=prefer` routes every prompt there while
`DISPLAY` is set, terminals included; a bare console falls back to the TTY,
and a GNOME session hands over to seahorse's GTK prompter (fuzzel needs a
layer-shell compositor).

| line | meaning |
|---|---|
| ``Request from `<command>` `` | the ssh/ssh-add command line asking - a wrong host or an unexpected caller stands out at once |
| `Unlock SSH key <name> (<comment>)` | which key; several candidates are listed by name |
| `passphrase ❯` | the masked input row |

For key prompts the dialog validates your input with a trial decryption of the
keys in `~/.ssh/id_*`: a wrong passphrase re-prompts with a red "Passphrase
rejected" line instead of a silent identical dialog. Esc cancels; the auth
fails cleanly and nothing is cached. Server password prompts are not validated
(a server password cannot decrypt a local key): they show ssh's own text with a
`password ❯` label and pass through untouched, and a second consecutive
rejection is handed to ssh as typed, so no prompt type can trap you in the red
loop. Keys referenced via `IdentityFile` outside `~/.ssh/id_*` get the generic
prompt without validation.

## agent-ssh: SSH with a human in the loop

The personal key sits decrypted in the agent, so any process running as you,
a coding agent included, could use it silently. `agent-ssh` is `ssh` pinned to
a separate passphrase-protected key, `~/.ssh/id_agent_ed25519`, with the
session agent bypassed:

```bash
agent-ssh ai_server            # canonical: the server alias
agent-ssh <user>@<host>        # ad hoc, still pins the agent key
```

| option | effect |
|---|---|
| `-i ~/.ssh/id_agent_ed25519` + `IdentitiesOnly=yes` | only the agent key is offered |
| `SSH_AUTH_SOCK` unset | the session agent cannot answer for it |
| `AddKeysToAgent=no` | a successful decryption is never cached; the next call prompts again |
| `SSH_ASKPASS_REQUIRE=force` | always the fuzzel dialog, which names the requesting command |
| `StrictHostKeyChecking=accept-new` | first contact accepted, a changed host key still fails |

Every use costs one dialog: you read the command line and type the passphrase
or press Esc. That passphrase must never pass through an agent's context; the
key was generated by hand (`ssh-keygen -t ed25519 -a 100`) and only its `.pub`
goes into servers' `authorized_keys`.

## The ai_server alias

`~/.ssh/config` is home-manager's and holds exactly one block, `Host ai_server`
(named like the ansible inventory in `~/dev/server_setup`): host name, the
`ai_ops` user, the agent key with `IdentitiesOnly`, and `AddKeysToAgent no`.
Every other host keeps resolving against `/etc/ssh/ssh_config`.

- `ssh ai_server` uses the agent key without the wrapper: no user@IP to
  remember, and tools that read `~/.ssh/config` (pi's ssh tools) see a named
  host. The block's `AddKeysToAgent no` keeps the key out of the session agent
  on this path too.
- `agent-ssh ai_server` is the same connection with the wrapper's guarantees
  on top; automation should use this form.

Multiplexing (`ControlMaster auto`, `ControlPersist 10m`, sockets at
`~/.ssh/cm-*`) means one passphrase per ten-minute burst of work rather than
per command. While a master socket lives, any process running as you can ride
it without a prompt; the gate is "approve each burst", not "approve every
call". A stale socket after a reboot is reaped by the next connection.

## pass and gpg

`pass` keeps secrets in `~/.password-store`, one file per entry, encrypted to
your single gpg key. `gpg-agent` runs as a user unit and caches the unlocked
key: the first `pass show` of a session asks for the gpg passphrase, the rest
are silent.

```bash
pass                              # tree of entries
pass show path/to/entry           # decrypt (first call prompts)
pass show -c path/to/entry        # to the clipboard instead of the terminal
pass insert path/to/entry
systemctl --user status gpg-agent.service
```

Which pinentry you get depends on the caller: interactive shells export
`PINENTRY_USER_DATA=tty`, so terminal callers get the curses prompt; anything
spawned from the session without a shell (qutebrowser's pass filling) gets the
GNOME dialog. Both unlock the same agent cache.

OTP lives in the browser, not the shell: the command-line `pass` has no `otp`
subcommand, the `pass-otp` extension is wired only into qutebrowser's
userscript. Login filling (`zl`, `zol`, the pass path layout, inserting OTP
entries) is in the [qutebrowser guide](./qutebrowser.html). Tools read the same
store: phi resolves credentials declared with `backend: pass` and a
`ref: path/to/entry` at start, so an API key lives in pass once and never in a
config file.

## gnome-keyring

`gnome-keyring-daemon` is started at login and unlocked by PAM with your
password; it owns `org.freedesktop.secrets` on the session bus for desktop
apps that store tokens that way. It has no part in SSH (its agent is off) or
in `pass`.
